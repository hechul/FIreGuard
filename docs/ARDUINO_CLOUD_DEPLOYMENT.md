# Arduino USB 장비 클라우드 연동 및 적용 순서

이 문서는 2026-11-09에 전달된 FireGuard 클라우드 전체 패치의 전송 규격을 기준으로 한다. 실제 장비의 매핑·발광 성공을 인증하지 않는다. Arduino와 Raspberry Pi의 로컬 제어 코드는 여기서 변경하지 않는다.

## 서버 배포 순서

1. 기존 Supabase 프로젝트의 SQL Editor에서 `supabase/migrations/202611090001_arduino_telemetry.sql` 전체를 실행한다. 기존 `ingest_telemetry`는 그대로 둔다.
2. 변경된 서버를 Vercel에 배포한다. 기존 boolean 센서 전송은 기존 RPC를 사용하고 새 USB 보고는 별도 `ingest_telemetry_v2`를 사용한다. SQL이 없으면 새 보고는 실패하며 옛 RPC에 대체 기록하지 않는다.
3. Pi 측 팀이 최신 패치를 적용하고 실제 센서·그래프·LED 매핑 버전이 일치하는지 확인한다. 서버는 전달된 버전 세 개만 허용한다. 교차점 등 실제 매핑을 변경해 해시가 바뀌면 변경 내용을 검증하고 서버 허용 버전도 변경해야 한다.
4. 실제 장치 테스트 전까지 `--cloud-preview`로 검토하고 합성 예시를 운영 DB에 넣지 않는다. 운영 전송은 REAL 상태에서만 한다. `operationMode: simulation`은 이 서버에서 거부한다.
5. 실제 센서 감지, 경로 없음, 센서 단절·복구, Arduino 연결·ACK 실패, 네트워크 단절 및 복구를 장비 담당자와 함께 확인한다. LED 위치와 방향은 실물 확인 전 미검증 상태다.

## 데이터 해석

- 센서 연결 끊김은 정상이나 화재 해제로 간주하지 않는다. 마지막 화재 값은 수집 RPC에서 원자적으로 보존하며 센서는 미확인으로 표시한다.
- `routeStatus=no_route`는 Pi 경로가 없다는 보고다. 서버가 계산한 다른 경로를 Pi 경로로 표시하지 않는다.
- `blockedEdges`는 그래프상 차단이고 빨간 LED 표시 계획과 별개다.
- 논리 LED 인덱스는 0..161, Arduino 슬롯은 0..162다. 논리 20 이상만 전송 시 +1이며 슬롯 20은 비워 둔다. N28/N35는 도면상 LED 62(논리 61, 전송 슬롯 62)를 공유하지만 위치 검증은 별도다.
- 계획값과 FLOW OK로 확인된 명령은 별도다. Arduino ACK는 명령 응답이며 LED 발광을 측정한 것이 아니다.
- DB의 관제 JSON은 기존 정책상 공개 읽기 대상이다. 장치 토큰 등 비밀을 telemetry에 넣지 않는다.

## Pi 패치에서 별도로 수정·확인할 점

전달받은 CloudReporter는 요청 응답에서 `accepted: false`를 성공으로 취급할 수 있고, HTTP 호출이 제어 루프를 최대 timeout 동안 지연시킬 수 있다. Pi 담당자는 중복/오래된 보고 응답을 검사하고 네트워크 전송을 별도 작업자로 분리한 뒤, 네트워크 장애에도 센서 및 USB 제어가 지연되지 않는지 검증해야 한다. DB 응답이 `accepted: false`면 새 스냅샷이 저장된 것이 아니다.
