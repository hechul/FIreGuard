# Pi → 배포 UI 연동 규격

이 문서는 첨부된 최신 `hardware/config.py`, `flame_multi_reader.py`를 기준으로 한 **새 클라우드 API 규격**입니다. 구버전 하드웨어 README의 주소·센서 ID는 사용하지 않습니다.

## 센서 연결 빠른 실행

`hardware/cloud_flame_reader.py`는 11개 GPIO를 읽어 이 규격으로 전송하는 센서 전용 프로그램입니다. 11개 센서의 배선과 GPIO 매핑을 확인하고, 기존에 동일 GPIO를 사용하는 센서 프로그램은 종료한 뒤 같은 토큰이 설정된 터미널에서 실행합니다.

```bash
python3 hardware/cloud_flame_reader.py
```

Pi에 `gpiozero`와 `lgpio`가 필요합니다. HIGH=정상/LOW=감지이며, 3회 연속 샘플 후 상태를 확정합니다. 11개 값이 모두 확정된 뒤 전송하고, 변경 시 즉시 및 약 5초마다 전체 상태를 보고합니다. HTTP는 별도 스레드에서 수행합니다. `Ctrl+C`로 종료합니다.

이 프로그램은 **LED 제어를 수행하지 않습니다.** LED 상태는 `unknown`으로 보고되며, Pi 담당자가 기존 LED 로직과 경로를 결합하고 적용 결과를 추가해야 합니다. 서버 또는 DB가 단절되면 센서 읽기를 계속하며 최신 상태를 다시 전송합니다.

## 주소와 인증

- `POST https://<배포주소>/api/hardware/telemetry`
- 클라우드 모드에서 `/api/hardware/batch`도 같은 규격을 받습니다. 구버전 `{ "flame": ... }`만 보내는 요청은 충분하지 않습니다.
- 헤더: `Content-Type: application/json`, `Authorization: Bearer <장치 토큰>`
- 토큰은 Vercel의 `FIREGUARD_DEVICE_TOKEN`과 Pi 환경변수에 같은 값으로 설정합니다. 최소 32자의 무작위 문자열을 사용하고 브라우저 코드·저장소·채팅에는 넣지 않습니다.
- `deviceId`는 서버의 `FIREGUARD_DEVICE_ID`와 같아야 합니다. 초기 기본값은 `pi-01`입니다.

## 센서 매핑

매핑 버전은 `flame-20261030-v1`입니다. 번호는 센서 고유 ID이며 노드 번호와 일치할 필요가 없습니다.

| 센서 | 노드 | BCM GPIO | 물리 핀 |
|---|---|---|---|
| FLM-01 | N20 | 23 | 16 |
| FLM-02 | N2 | 27 | 13 |
| FLM-03 | N3 | 22 | 15 |
| FLM-04 | N4 | 5 | 29 |
| FLM-05 | N5 | 6 | 31 |
| FLM-06 | N6 | 13 | 33 |
| FLM-07 | N7 | 19 | 35 |
| FLM-08 | N8 | 12 | 32 |
| FLM-09 | N9 | 16 | 36 |
| FLM-10 | N10 | 20 | 38 |
| FLM-11 | N11 | 21 | 40 |

실물 위치와 현재 도면의 노드 의미를 한 번씩 대조한 뒤 사용합니다. `FLM-03`은 이 규격에서 N3이며, 구버전 UI의 `FLM-03 → N9`와 다릅니다.

## 전송 본문

```json
{
  "deviceId": "pi-01",
  "bootId": "f9ceda01-ece4-4615-9c25-14dfe38e312c",
  "sequence": 0,
  "observedAt": "2026-10-30T03:00:00+00:00",
  "mappingVersion": "flame-20261030-v1",
  "startNode": "N33",
  "flame": {
    "FLM-01": false,
    "FLM-02": false,
    "FLM-03": false,
    "FLM-04": false,
    "FLM-05": false,
    "FLM-06": false,
    "FLM-07": false,
    "FLM-08": true,
    "FLM-09": false,
    "FLM-10": false,
    "FLM-11": false
  },
  "led": {
    "status": "unknown",
    "routeId": null,
    "segments": [],
    "error": null
  }
}
```

예시의 시각을 그대로 재사용하지 말고 실제 전송 때 UTC 시각을 생성합니다.

| 필드 | 규칙 |
|---|---|
| `bootId` | Pi 수집 프로세스 시작 때 UUID 한 번 생성. 실행 중 재사용 |
| `sequence` | 같은 bootId 안에서 전송할 때마다 증가하는 0 이상의 정수 |
| `observedAt` | 센서를 읽은 시각. UTC 또는 시간대가 포함된 ISO 8601. 서버 기준 과거 5분~미래 60초 범위 |
| `mappingVersion` | 위 매핑 버전과 일치 |
| `flame` | **매 요청마다 센서 11개 모두** 포함. JSON `true`/`false`만 사용 |
| `startNode` | 선택 사항. 기본 N33. 경로가 포함되면 첫 노드와 일치 |
| `route` | 선택 사항. Pi가 계산한 경로. 아래 참고 |
| `led` | 선택 사항. 생략 시 미확인. 센서 감지만으로 적용 완료를 추정하지 않음 |

기존 코드의 ACTIVE LOW 판단과 연속 샘플 필터는 유지할 수 있습니다. 서버에는 raw HIGH/LOW 대신 **판단된 감지 여부**를 보냅니다. 센서 하나만 변해도 11개 전체 확정 상태를 전송하고, 변화가 없을 때도 약 5초마다 전체 상태를 보냅니다. 아직 초기값이 확정되지 않은 채널을 정상으로 만들어 전송하지 않습니다.

같은 bootId·sequence를 재전송해도 현재 상태나 이벤트가 중복 생성되지 않습니다. 오래된 순번·시각은 최신 상태를 덮어쓰지 않습니다. Pi 시각 동기화를 켜두고 센서 수집·LED 처리와 네트워크 전송을 분리합니다.

## 경로와 LED 결과

Pi에서 경로를 계산했다면 `route`에 다음 형식을 포함합니다. 실제 지도 노드·간선과 순서가 맞는 경로여야 하며, 위험 노드를 통과하는 경로는 허용하지 않습니다.

```text
route.id            Pi가 생성한 경로 식별자
route.nodes         출발점부터 대피지점까지의 노드 ID 배열
route.edges         위 노드들을 순서대로 잇는 간선 ID 배열
route.destinationId 마지막 대피지점 ID
route.cost          0 이상의 유한한 경로 비용
```

`led.status` 값은 다음과 같습니다.

- `unknown`: 출력 결과를 아직 보고하지 않음. 초기 센서 연결 단계에서 사용
- `applied`: Pi 코드가 해당 경로의 LED 출력을 적용함. 유효한 `route`와 같은 `led.routeId` 필수
- `error`: 출력 처리 실패. `led.error`에 256자 이내 설명

`led.segments`는 적용 결과를 보고할 구간 배열입니다.

```json
[{"id": "S1", "on": true, "color": "#00ff00"}]
```

LED 구간은 현재 하드웨어 정의의 `S1`~`S15`입니다. 이 예시가 어떤 대피 경로와 연결되는지는 주장하지 않습니다. 실제 구간 대응표가 확정되기 전까지 UI의 3D LED는 중립색으로 표시하고 보고된 구간은 텍스트로 확인합니다. `applied`는 **Pi의 출력 적용 보고**이며 별도 광학·전류 피드백으로 실제 점등을 측정했다는 뜻은 아닙니다.

Pi 경로를 보내지 않으면 UI에는 서버가 계산한 **미리보기 경로**가 표시됩니다. 이 경로는 Pi가 사용한 경로로 표시되지 않으며 LED 적용 완료의 근거가 되지 않습니다.

## 통신 결과 처리

- 성공 응답의 `accepted`가 `true`면 새 스냅샷이 저장된 것입니다.
- `accepted: false`는 중복 또는 오래된 전송이므로 전송 순번·Pi 시각을 확인합니다.
- `400`: 필드, deviceId, 센서 매핑, 경로 또는 LED 보고 형식 확인
- `401`: 장치 토큰 확인
- `503`: DB 설정 또는 통신 장애. 로컬 제어를 유지하고 최신 전체 상태를 재시도

서버의 응답으로 Pi를 원격 제어하는 기능은 이번 범위에 없습니다. 센서 판단·경로 계산·LED 출력은 Pi 담당 코드에서 수행하며 API는 결과를 수신합니다.

## 친구에게 전달할 구현 순서

1. 새 주소·토큰·deviceId를 환경변수에서 읽기
2. 시작 시 bootId 생성, sequence 관리, 전체 11채널 스냅샷 전송
3. 센서 → 노드 → 로컬 경로 → LED 출력을 연결
4. 경로와 LED 적용/오류 결과를 같은 전송에 포함
5. 서버가 끊겨도 로컬 처리 유지, 복구되면 최신 전체 상태 재전송
6. 실제 센서 하나부터 배포 UI의 노드·로그를 대조하고 11개로 확대
